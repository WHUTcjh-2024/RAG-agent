# 购物袋数量控制设计

## 目标

为已登录用户的购物袋增加移动端友好的数量增减操作。前端复用现有 Java 购物车更新接口，不调整 Python RAG 主流程，也不改变购物车、订单的数据模型。

## 交互规则

- 每个购物车商品展示紧凑的 `减号 - 数量 - 加号` 步进器。
- 数量最小为 1；数量为 1 时，减号禁用。
- 删除商品仍使用独立的“移除”操作，不把减号作为删除入口。
- 用户点击加号或减号后，数量控件立即进入等待状态，防止连续请求造成乱序覆盖。
- 某个商品的数量正在更新时，该商品的加减与移除操作禁用；结算和清空购物车也暂时禁用，避免按旧数量创建订单。

## 前端结构

### API 客户端

在 `frontend/src/api/client.ts` 增加更新数量函数，调用：

`PATCH /api/cart/items/{itemId}`

请求携带当前登录用户的 Bearer Token，JSON 请求体仅包含 `quantity`。接口成功后返回购物车项；页面仍重新拉取整个购物车，以统一刷新购物袋数量、总价和顶部角标。

### 页面与组件

`App.tsx` 负责数量更新生命周期：保存当前正在更新的购物车项 ID，调用 API，并在成功后重新获取购物车；失败时复用现有提示区域展示错误。

`CartDrawer` 只负责展示和触发：接收数量更新回调与正在更新的项 ID，渲染图标按钮、禁用状态及可访问名称。数量控件使用现有 Lucide 图标，不引入新的依赖。

样式仅调整购物袋项目区域：为步进器和移除按钮增加明确的独立选择器，保持现有移动端信息密度和配色，不改动其他页面。

## 数据流与异常处理

1. 用户点击加号或减号。
2. 页面将该商品标记为更新中，并调用 Java 购物车 PATCH 接口。
3. 成功后重新请求 `GET /api/cart`，用返回数据刷新状态和总价。
4. 请求失败时保留原数量，显示已有的错误提示。
5. 无论成功或失败，解除该商品的更新中状态。

后端已验证数量不小于 1，并基于 JWT 当前用户限制购物车项归属；前端禁用减号是用户体验保护，不替代后端校验。

## 测试与验收

- 为 API 客户端增加单元测试，验证 PATCH 方法、认证请求头、数量请求体与响应解析。
- 运行前端单元测试与生产构建。
- 在虚拟机部署后，使用已登录账号验证：加一、减一、数量为 1 时减号禁用、移除、总价和顶部角标刷新、更新期间不能结算、数量变化后正常下单。

## 非目标

- 不修改 Python RAG、商品推荐、向量索引或数据集导入流程。
- 不迁移 Java 商品系统。
- 不增加库存扣减、最大购买数量或购物车商品勾选逻辑。
